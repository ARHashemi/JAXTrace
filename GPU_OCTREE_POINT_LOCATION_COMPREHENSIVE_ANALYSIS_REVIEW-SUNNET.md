### 1. Is my approach octree-aware Morton like the referenced paper?

**Your approach is simpler and slightly less robust than the paper's method.**

*   **The Paper (Baert et al.):** Uses a "loose" or "dual" structure where elements are pushed down to the *finest octant that fully contains them*. This guarantees that if you traverse the tree to a leaf, you also check the parent nodes for large elements that overlap the leaf.
*   **Your Method:** Assigns each element to **exactly one leaf** based on its **centroid**.
    *   *Critique:* This is why you have the failure mode described in your analysis (Section 5.1). An element can span 8 octants but is only stored in one. If a particle is in the corner of that element (in a different octant), and your search radius isn't large enough to hit the centroid's octant, you miss it.
*   **Conclusion:** You are *not* doing the full hierarchical traversal of the paper. You are doing a "flat" search on a sorted list. The paper's method is "more improved" because it handles element span explicitly, whereas you rely on `radius` to "hope" you catch the neighbor.

### 2. Can I assign elements by bounding box instead of centroid?

**Yes, but it leads to the "Redundant Storage" path you correctly identified as expensive.**

*   **The Trade-off:**
    *   **Centroid (Current):** 1 element $\to$ 1 leaf. Efficient, but geometric misses possible.
    *   **Bounding Box (Redundant):** 1 element $\to$ N leaves (all leaves it touches).
*   **Is there a better method?**
    *   **Yes: The "Loose Octree" / Parent Storage approach.**
    *   Instead of storing the element in *all* touched leaves (too much memory), store it in the **smallest parent node** that fully contains it.
    *   *Search Modification:* When searching for a point in Leaf X, you must search **Leaf X + Parent(X) + Parent(Parent(X))... up to Root.**
    *   *Why this helps:* Large elements live in upper nodes. Small elements live in leaves. You never miss a large element because you always check the parents.
    *   *GPU Cost:* Requires checking ~4-5 extra nodes (the parents) per query. This is likely cheaper than increasing `radius` to 30 or 60.

### 3. Can I align the octree with the Kuhn mesh's intrinsic octree?

**Yes, and this is the "Golden Path" for your specific mesh.**

*   **Why:** Your mesh is *already* generated by an octree refiner. The elements *perfectly* align with octant boundaries (except for the diagonal cuts).
*   **The Strategy:**
    1.  **Force Octree Depth:** When building your Morton octree, **force the leaf depth** to match the mesh refinement level at that location.
    2.  **Align Leaves:** Ensure your octree leaves correspond exactly to the grid cells of the mesh generator.
    3.  **Result:** Every element (Kuhn tet) will be contained *almost* entirely within one octant (since they are subdivisions of a cube).
    4.  **Edge Case:** Kuhn tets share faces on the grid lines. Floating point errors might put a particle "on the line."
    5.  **Solution:** This aligns perfectly with your **Epsilon Tolerance Fix**. If the tree matches the mesh, the only misses are numerical.
