# Research Report: Extracting Intrinsic Octree Structure from Kuhn Tetrahedral Meshes

## Context and Problem Statement

The mesh under consideration is generated by adaptive octree refinement where each cube is subdivided into 6 Kuhn tetrahedra sharing a body diagonal. The mesh contains approximately 3 million elements across refinement levels 8-14, with 2:1 balance enforced. The goal is to extract the intrinsic octree structure from this tetrahedral mesh for efficient GPU-based point location.

---

## 1. Methods for Extracting Octree Structure from Kuhn Meshes

### Method A: Permutation-Based Parent Cube Identification (RECOMMENDED PRIMARY)

The Freudenthal-Kuhn triangulation has a mathematically exact relationship between simplices and their parent cubes. Each tetrahedron in a Kuhn subdivision corresponds to a specific permutation of coordinates.

**Algorithm (from FreudenthalTriangulations.jl and the SoCG 2021 paper):**

For a **uniform** Kuhn mesh, given a point x:
1. Compute the parent cube corner: `v = floor(x)` (in normalized coordinates)
2. Compute displacement: `d = x - v`
3. Sort components of d in descending order to get permutation p
4. The simplex is uniquely identified by the pair `(v, p)` -- the "permutahedral representation"

**For reconstructing parent cubes from known tetrahedra:**

Given a tetrahedron with vertices `{v0, v1, v2, v3}`, the parent cube is the axis-aligned cube whose vertices include the two endpoints of the body diagonal. In a Kuhn subdivision:
- All 6 tetrahedra in one cube share the same body diagonal edge
- The body diagonal connects two opposite cube corners (e.g., (0,0,0) to (1,1,1) in normalized coordinates)
- The body diagonal is the unique edge of length `sqrt(3) * cell_size` (the longest edge)

**Strengths:**
- Mathematically exact -- no tolerance parameters needed
- O(1) per element (just find the diagonal, compute cube corner)
- The permutahedral representation is compact: just (corner_vertex, permutation)

**Weaknesses:**
- Assumes all tetrahedra are "true" Kuhn tetrahedra (exactly 3 axis-aligned edges)
- Does NOT directly apply to non-Kuhn transition elements at refinement boundaries

### Method B: Diagonal-Based Grouping (Method 2 from reference doc)

This is essentially Method A applied via grouping: identify the body diagonal of each tetrahedron, group all tetrahedra sharing the same diagonal, and verify groups of 6.

**Convergence Risks and Robustness Concerns:**

1. **Ambiguous longest edge**: In a true Kuhn tetrahedron, the edge lengths are precisely `cell_size` (3 axis-aligned edges), `sqrt(2) * cell_size` (2 face diagonal edges), and `sqrt(3) * cell_size` (1 body diagonal). The ratios are 1 : sqrt(2) : sqrt(3), meaning the body diagonal is ~22.5% longer than the face diagonals. This gap is large enough that floating-point comparison is safe for identifying the longest edge in well-formed Kuhn tetrahedra.

2. **Floating-point comparison risk**: The real risk is NOT ambiguity between face diagonals and body diagonals (they differ by 22.5%). The risk is:
   - In anisotropic meshes (your mesh has X/Y ratio = 0.9783, Y/Z = 1.0222), the "body diagonal" length is `sqrt(dx^2 + dy^2 + dz^2)`, and the face diagonals have lengths like `sqrt(dx^2 + dy^2)`. With mild anisotropy, the gap remains safe.
   - Compare squared lengths (avoid square roots) for robustness: `dx^2 + dy^2 + dz^2` vs `dx^2 + dy^2`, `dx^2 + dz^2`, `dy^2 + dz^2`. The body diagonal squared always dominates.

3. **Critical concern**: This method fails completely for the ~1,826 non-Kuhn elements that have NO axis-aligned edges.

### Method C: Axis-Aligned Edge Detection (Current Implementation)

The current code (`find_axis_aligned_edges_single()`) detects 3 axis-aligned edges per tetrahedron to infer cell_size and refinement level.

**Strengths:**
- Directly identifies the cell size from edge lengths
- Works well for standard Kuhn tetrahedra (99.94% of elements)

**Weaknesses:**
- Fails for non-Kuhn transition elements (0.06% = 1,826 elements)
- The parent cube identification step (`find_parent_cube()`) had a critical bug (using v_min instead of centroid), leading to 82.3% failure rate

### Method D: Hanging Node Detection (Recommended by reference doc as Method 1)

**Algorithm:**
A hanging node is a vertex that falls on the edge or face of a larger element but is not a vertex of that element. In a 2:1 balanced octree, hanging nodes appear ONLY at refinement boundaries where the level changes by exactly 1.

**How it works for octree extraction:**
1. For each vertex, check if it lies on an edge/face of a non-adjacent element
2. Hanging nodes mark refinement level transitions
3. From hanging node positions, reconstruct the parent-child octree hierarchy

**Strengths:**
- Directly encodes the refinement hierarchy
- No geometric tolerance issues for edge comparison
- Preserves 2:1 balance by construction

**Weaknesses:**
- Computationally expensive: requires checking every vertex against all neighboring elements
- Requires full mesh adjacency information
- Complex implementation
- Does NOT directly give you the parent cube of each element; it gives you the octree HIERARCHY

### Method E: Vertex-Based Cube Reconstruction (Pellerin et al. 2017)

The paper "Identifying combinations of tetrahedra into hexahedra: a vertex based strategy" by Pellerin, Johnen, and Remacle provides an algorithm that searches for sets of 8 vertices whose connectivity forms a valid hexahedron.

**How it could apply:**
1. For each vertex in the mesh, search for 7 other vertices that form a cube
2. The 6 tetrahedra sharing the body diagonal of this cube are all children
3. Uses only mesh topology (connectivity), not geometry

**Strengths:**
- Pattern-free (doesn't assume Kuhn structure)
- Finds ALL valid cube reconstructions
- Handles non-standard decompositions

**Weaknesses:**
- Overkill for this problem (designed for general tet-to-hex conversion)
- Slower than exploiting known Kuhn structure
- ~3M potential hexahedra in 10 seconds on laptop (acceptable but unnecessary)

## 2. Handling Non-Kuhn Elements at Refinement Boundaries

### What Are These Elements?

The ~1,826 non-Kuhn elements (0.06%) at refinement boundaries are **transition elements** created during red-green refinement to maintain mesh conformity at 2:1 balance boundaries.

### How They Arise

In octree-based adaptive mesh refinement with Kuhn subdivision:

1. **Red refinement (regular):** A cube is split into 8 child cubes, each subdivided into 6 Kuhn tetrahedra. All children are "red" and maintain Kuhn structure.

2. **Green refinement (irregular closure):** When a red-refined region is adjacent to an unrefined region, T-junctions (hanging nodes) appear at edge/face midpoints. Green refinement adds irregular tetrahedra to close these gaps WITHOUT full subdivision.

3. **Properties of green/transition elements:**
   - They do NOT have 3 axis-aligned edges
   - They do NOT share a body diagonal of any cube
   - They bridge elements of different refinement levels
   - They are NEVER further refined (if more resolution is needed, they are removed and their parent is red-refined)

### Handling Strategies

**Strategy 1: Skip and Assign by Proximity (RECOMMENDED)**

Since non-Kuhn elements are only 0.06% of the mesh:
1. Detect non-Kuhn elements (no axis-aligned edges found)
2. Compute their centroid
3. Assign them to the nearest octree cell (by centroid grid lookup)
4. Mark them as "transition" elements in the cell data

This is already essentially what the current code does (skipping with `n_skipped += 1`), but those elements should be assigned rather than skipped entirely.

**Strategy 2: Assign to Coarser Parent Cell**

Transition elements bridge two refinement levels. Assign them to the coarser cell:
1. Find the longest edge of the transition tetrahedron
2. The longest edge length corresponds to the coarser refinement level
3. Assign to the cell at that coarser level containing the centroid

**Strategy 3: Multi-Insert into Both Adjacent Cells**

Since transition elements span the boundary between two refinement levels:
1. Compute the element bounding box
2. Find all octree cells it overlaps
3. Insert into all of them (typically 2-4 cells)

This adds only 2-4 * 1,826 = 3,652-7,304 extra entries (negligible for 3M elements).

### Recommendation

**Use Strategy 1 (assign by centroid proximity) for the 0.06% non-Kuhn elements.** The impact is negligible:
- Worst case: ~1,826 elements slightly mislocated
- Since they are searched via neighbor fallback anyway, exact cell assignment is less critical
- Alternatively, Strategy 3 (multi-insert) is also cheap and guarantees finding them

## 3. Alternative Approaches

### 3.1 Pure Vertex-Based Cube Reconstruction

Instead of using edge properties, reconstruct cubes purely from vertex positions:

1. **Round vertices to grid**: For each refinement level L, compute `grid_pos = round(vertex / cell_size_L)`. Vertices that round to all 8 corners of a cube define that cube.

2. **Group by cube corners**: For each pair of diagonally opposite vertices (potential body diagonal), check if the other 6 cube corners exist in the vertex set.

**Advantage:** Works without ANY edge-based analysis. Pure vertex position matching.
**Disadvantage:** Requires O(n_vertices * n_levels) work, but with hash tables this is O(n_vertices) per level.

### 3.2 Morton Code + Level Identification (Current Approach, Enhanced)

The current implementation's approach of (Morton code, level) pairs as cell keys is fundamentally sound. The critical fix needed is:

1. **Fix parent cube identification**: Use centroid (already done in latest code) or, better, use the Kuhn diagonal method
2. **Handle non-Kuhn elements**: Assign by centroid to nearest cell
3. **Add neighbor search**: For particles near cell boundaries, search 26 spatial neighbors

### 3.3 Hybrid: Axis-Aligned Edge + Diagonal Verification

A robust two-pass approach:

**Pass 1 (99.94% of elements):**
1. Find 3 axis-aligned edges -> infer cell_size and level
2. Compute centroid -> assign to grid cell
3. Verify: all 4 vertices fall within the cell or its immediate neighbors

**Pass 2 (0.06% non-Kuhn elements):**
1. No axis-aligned edges found
2. Compute centroid, assign to cell at level inferred from longest edge
3. Mark as transition element

**Pass 3 (verification):**
1. Group elements by cell
2. Verify Kuhn cells have exactly 6 elements
3. Flag cells with non-6 counts as refinement boundary cells (expect 12, 24, or irregular counts)

## 4. Robustness Considerations for Diagonal-Based Grouping

### 4.1 Is the Diagonal Ambiguous?

**No, for true Kuhn tetrahedra.** The edge lengths in a Kuhn tetrahedron from a cube with side lengths (dx, dy, dz) are:

| Edge Type | Count | Squared Length | Example (isotropic) |
|-----------|-------|----------------|---------------------|
| Axis-aligned | 3 | dx^2, dy^2, dz^2 | 1.0 |
| Face diagonal | 2 | dx^2+dy^2, dx^2+dz^2, or dy^2+dz^2 | 2.0 |
| Body diagonal | 1 | dx^2+dy^2+dz^2 | 3.0 |

The body diagonal squared is ALWAYS larger than any face diagonal squared:
- `dx^2 + dy^2 + dz^2 > dx^2 + dy^2` (since dz^2 > 0)
- `dx^2 + dy^2 + dz^2 > dx^2 + dz^2` (since dy^2 > 0)
- `dx^2 + dy^2 + dz^2 > dy^2 + dz^2` (since dx^2 > 0)

**With your anisotropy (X/Y = 0.9783, Y/Z = 1.0222):**
- dx = 0.0000781250, dy = 0.0000798612, dz = 0.0000781250 (at level 14)
- Body diagonal^2 = dx^2 + dy^2 + dz^2 = 1.859e-8
- Max face diagonal^2 = dx^2 + dy^2 = 1.249e-8
- Ratio: 1.488 (body diagonal^2 / max face diagonal^2)
- **Gap: 49% difference in squared length** -- completely unambiguous

### 4.2 When Could It Fail?

The diagonal identification could theoretically fail if:

1. **Degenerate tetrahedra**: A tet where one axis-aligned edge has length approaching zero (dx -> 0). Then the body diagonal length approaches `sqrt(dy^2 + dz^2)`, which equals a face diagonal. This does NOT occur in well-formed Kuhn meshes.

2. **Non-Kuhn tetrahedra**: The 1,826 transition elements have NO axis-aligned edges, so the concept of "body diagonal" doesn't apply. These must be handled separately.

3. **Floating-point edge cases**: Using squared lengths and comparing `a^2 + b^2 + c^2 > a^2 + b^2` reduces to `c^2 > 0`, which is always true for non-degenerate tetrahedra. No tolerance needed.

### 4.3 Shewchuk's Robust Predicates

For geometric computations in computational geometry, Jonathan Shewchuk's robust geometric predicates provide exact arithmetic when floating-point comparison is unreliable. However, **for this specific problem (longest edge identification in Kuhn tetrahedra), robust predicates are NOT needed** because:

- The gap between body diagonal and face diagonal is ~49% in squared length
- This gap far exceeds floating-point epsilon (~1e-15 for float64)
- Simple squared-length comparison is sufficient

The only place where geometric robustness matters is point-in-tetrahedron testing, which uses barycentric coordinate computation.

### 4.4 Recommendation for Robustness

Use **squared edge lengths** for diagonal identification:

```python
def identify_body_diagonal(vertices):
    """Find the body diagonal (longest edge) of a Kuhn tetrahedron."""
    edges = [(i,j) for i in range(4) for j in range(i+1, 4)]  # 6 edges
    sq_lengths = [sum((vertices[i] - vertices[j])**2) for i,j in edges]
    max_idx = argmax(sq_lengths)

    # Verify: body diagonal should be ~50% longer (squared) than next longest
    sorted_sq = sorted(sq_lengths, reverse=True)
    ratio = sorted_sq[0] / sorted_sq[1]  # Should be ~1.5 for isotropic

    if ratio < 1.2:  # Safety threshold
        # WARNING: ambiguous diagonal -- non-Kuhn element
        return None

    return edges[max_idx]  # (vertex_i, vertex_j) of body diagonal
```

The ratio check (threshold 1.2) catches non-Kuhn elements that lack a clear diagonal, providing a natural fallback mechanism.

## 5. Comprehensive Recommendation

### Recommended Algorithm: Hybrid Axis-Aligned + Diagonal Method

**Phase 1: Element Classification (O(n_elements))**

For each tetrahedron:
1. Compute all 6 edge vectors
2. Check for 3 axis-aligned edges (tolerance 1e-6)
3. If 3 axis-aligned edges found -> classify as Kuhn, extract cell_size and level
4. If not -> identify longest edge, check ratio threshold
   - If ratio > 1.2 -> likely non-standard Kuhn (still has diagonal)
   - If ratio < 1.2 -> classify as transition/non-Kuhn

**Phase 2: Parent Cube Assignment (O(n_elements))**

For Kuhn elements (99.94%):
1. The cell_size comes from axis-aligned edge lengths
2. The parent cube is identified by: `cube_corner = floor(centroid / cell_size) * cell_size`
3. Alternatively (more robust): the body diagonal endpoints define the cube. The cube corner is `min(diag_v0, diag_v1)` component-wise, and the opposite corner is `max(diag_v0, diag_v1)` component-wise.
4. Encode as (Morton code, level) key

For non-Kuhn elements (0.06%):
1. Infer level from longest edge length
2. Assign to cell containing centroid at that level
3. Optionally: multi-insert into 2-4 overlapping cells (cheap, only 1,826 elements)

**Phase 3: Verification (O(n_cells))**

1. Count elements per cell
2. Standard Kuhn cells: exactly 6 elements
3. Refinement boundary cells: 12, 24, or irregular counts
4. Cells with transition elements: 6 + small number of non-Kuhn

**Phase 4: GPU Data Structure**

1. Store (Morton, level) pairs sorted for binary search
2. CSR format for cell-to-element mapping
3. Level-indexed cell sizes for fast grid computation
4. Neighbor search capability: for each query position, check primary cell + 26 spatial neighbors + parent level cell

### Why the Diagonal Method (Method B) IS Safe

Despite the reference doc's concerns about convergence risk:

1. **The body diagonal is ALWAYS unambiguously the longest edge** in any non-degenerate Kuhn tetrahedron (49% gap in squared length, even with anisotropy)

2. **The only elements where diagonal identification fails are non-Kuhn transition elements** -- and these are already identifiable by the absence of axis-aligned edges

3. **Using squared lengths eliminates square root computation** and avoids any floating-point accumulation

4. **The ratio test (body/face diagonal ratio) provides a natural classifier** that simultaneously identifies the diagonal AND detects non-Kuhn elements

### Critical: The Real Problem Is Not Diagonal Identification

Based on reviewing the project documentation, the actual critical issues are:

1. **Parent cube assignment**: The original bug (using v_min instead of centroid) caused 82.3% failure. The fix (using centroid) is correct but still has the limitation that elements spanning multiple cells will only appear in one cell.

2. **Elements spanning cell boundaries**: 25.4% of elements have their centroid in one cell but extend into neighboring cells. This is the fundamental limitation of single-cell assignment, regardless of how the parent cube is identified.

3. **Search strategy**: The key to high searchability is NOT better parent cube identification (the centroid fix largely solves this), but rather implementing a **spatial neighbor search** that checks adjacent cells when the primary cell doesn't contain the query point.

### Final Assessment

| Method | Reliability | Speed | Handles Non-Kuhn | Implementation Complexity |
|--------|-------------|-------|-------------------|--------------------------|
| Axis-aligned edges (current) | 99.94% | Fast | No (skips them) | Already done |
| Diagonal-based grouping | 99.94% | Fast | No (fails on them) | Simple |
| Hanging node detection | 100% | Slow | Yes | Complex |
| Vertex-based reconstruction | 100% | Medium | Yes | Medium |
| **Hybrid axis + diagonal** | **100%** | **Fast** | **Yes (with fallback)** | **Medium** |

The hybrid approach (axis-aligned edge detection for Kuhn elements + centroid-based assignment for non-Kuhn elements) provides the best balance of reliability, speed, and implementation complexity.
