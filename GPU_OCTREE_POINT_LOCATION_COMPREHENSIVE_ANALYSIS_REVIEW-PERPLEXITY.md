1. Your approach vs BLD13-style octree

Your current structure is a **linear, Morton-ordered adaptive octree with single-assignment of elements to leaves**, plus a 1D radius search along the leaf array. That is **octree-aware**, but it is **not** the same as the geometrically coherent, node-based traversal shown in Figure 1 of BLD13. Their method traverses explicit nodes and bounding boxes in 3D; yours traverses leaves in Morton index space with a bounded ±radius window. It is also not “more improved” in correctness: you deliberately traded the full coverage of a bounding-volume traversal for bounded 1D radius and lower memory traffic. 2. Bounding boxes vs centroids for leaf assignment

Your own analysis is correct: **centroid-only assignment is the main geometric failure mode** when a large element spans many leaves but is stored in only one. Assigning elements to **all leaves whose octant box intersects their element bounding box** is the classical fix and exactly what vtkCellLocator does. On GPU this: [ppl-ai-file-upload.s3.amazonaws](https://ppl-ai-file-upload.s3.amazonaws.com/web/direct-files/collection_6462cb8f-df5c-4317-bea4-bbba5ac5557e/b022530f-0234-4c52-922c-cec4123d9250/1-s2.0-S004578252400793X-main.pdf)

- Eliminates the “element lives four leaves away” problem.
- Costs roughly 4–8× more element references and hurts bandwidth.

There are middle-ground variants you did not like in the analysis, but that are worth stressing:

- **Shallow redundant assignment:** only duplicate elements across **coarse-level octants**, while leaves themselves still use single-assignment. You then:
  - Use octant-level lists for L2 “global” search.
  - Keep fine Morton leaves for cache-coherent iteration.
- **Hybrid masks:** per leaf, store a compact bitmask or small index list of “crossing coarse elements” from neighboring octants, not full duplication at every depth.

Both reduce—not remove—the centroid problem while keeping memory growth closer to 2–3× than 8×. They are still compromises, but they are **real solutions** to this specific geometric gap; your skepticism comes mainly from the bandwidth cost.

3. Matching search octree to Kuhn mesh octree

Conceptually: **yes, this is possible and attractive for your mesh**, but only if you respect the actual refinement structure.

Your Kuhn mesh is generated by octree-like 1:2 refinements with axis-aligned, power-of-two edge lengths. That means: [ppl-ai-file-upload.s3.amazonaws](https://ppl-ai-file-upload.s3.amazonaws.com/web/direct-files/attachments/70091334/9c86d3a8-3d38-43f3-8c06-7207a10fbf2a/diagnose_aa_tolerance.log)

- Each cell belongs to a unique logical octant at some depth.
- Element edges are aligned with the same dyadic grid that Morton/Hilbert use.

So in principle you can:

- Use the mesh generator’s logical cell indices (or derived cube IDs) to define your **octree nodes exactly as the mesh’s refinement tree**.
- Store **per-octant element lists** where each Kuhn tetrahedron is associated with its parent cube’s octant(s), not with the centroid-derived Morton code.
- Build your Morton/Hilbert keys from those logical cube IDs rather than recomputing codes from floating-point coordinates.

If you do that carefully, then:

- Octant boundaries and mesh cube boundaries coincide.
- You can guarantee that **no element’s cube is split across octants**, because that is how the mesh was refined.

But two critical caveats:

- Kuhn tetrahedra in a cube are still **subcells inside the cube**. A tetrahedron can geometrically cross a child octant boundary of a deeper tree than the mesh uses. To avoid “extension between leaves” you must **stop octree refinement at the same level as the coarsest cube that fully contains the tet**, not arbitrarily deeper.
- If your current octree builder subdivides purely by **element centroid density**, it is **not** aligned to the mesh’s logical cubes, even if both use powers of two. To “match the intrinsic octree,” you have to rebuild the tree using the mesh’s discrete cube indices rather than continuous bounding boxes.

So your idea is sound and would be a genuine improvement over centroid-based assignment, especially for a Kuhn/octree mesh. It is, however, a different builder than the one you have now; treating the current structure as already “perfectly aligned to Kuhn cells” would be incorrect.

It is fair to say those are **trade-offs, not clean fixes**—you are right to be dissatisfied if the goal is “100% retention at CPU-like speed.” The genuinely different directions that remain are:

- Fixing **numerical tolerance** in point-in-tet (you already identified `1e-10` as too tight; `1e-6` is a realistic float32-level tolerance).
