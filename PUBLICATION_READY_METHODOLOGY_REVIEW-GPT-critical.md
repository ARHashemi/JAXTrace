## Octree vs “leaf buckets”

Your Section 6.4 “Adaptive Octree Leaf Generation” algorithm is not building an octree by recursive spatial subdivision; it **sorts elements by Morton code and chunks the sorted list into fixed-capacity blocks**, then assigns each block a “depth” based on the common prefix of the first/last Morton code in the block.  This is closer to the family of “linear/implicit tree” constructions used in Morton-key BVHs and linear octree representations, where tree structure is inferred from key prefixes rather than stored as explicit pointers. [iccvm](https://iccvm.org/2020/docs/paper5.pdf)

Two practical implications:

- If a “leaf” is defined by arbitrary contiguous ranges in sorted Morton order, that range is not guaranteed to correspond exactly to a single octree cell (a pure prefix range); it is a **cluster** of keys whose minimal enclosing prefix defines some ancestor cell, but the leaf itself may cover only a subset of that cell’s key-space. [ppl-ai-file-upload.s3.amazonaws](https://ppl-ai-file-upload.s3.amazonaws.com/web/direct-files/attachments/70091334/4321f9a0-6805-4e03-8d8f-b26f318dc77d/PUBLICATION_READY_METHODOLOGY.md)
- Your prefix table (mapping from a fixed table-depth prefix to a [first_leaf,last_leaf] range) is consistent with “prefix/range acceleration” patterns used in linear tree indexing, but it is not the same as “tree traversal,” and the paper should name it accordingly to avoid reviewer pushback (“this is not an octree; it’s a bucketed Morton index”). [thomas.lewiner](http://thomas.lewiner.org/pdfs/octree_cgf.pdf)

So, to your question: it is reasonable to call it a **linear octree / implicit octree over Morton (or Hilbert) indices** if you explicitly define nodes via prefixes and ranges, but with the current described leaf construction it is more precise to say: **“SFC-sorted buckets + prefix-table lookup”**. [d-nb](https://d-nb.info/1217140409/34)
